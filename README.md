## 📌 ภาพรวมโครงงาน (Project Overview)

### 1. ที่มาและปัญหาที่พบ (The Problem)
ในปัจจุบัน นิสิตและบุคลากรของมหาวิทยาลัยพะเยาพึ่งพากลุ่ม Facebook หรือโซเชียลมีเดียในการสื่อสารเป็นหลัก แต่ต้องเผชิญกับปัญหาสำคัญ 3 ประการ:
* **❌ ข้อมูลปะปนกระจัดกระจาย (Information Chaos):** โพสต์ข่าวกิจกรรม ประกาศของหาย รีวิวร้านค้า และเรื่องร้องเรียนแจ้งซ่อม ถูกมัดรวมอยู่ในฟีดเดียว ทำให้อ่านยากและไม่เป็นระเบียบ
* **❌ โพสต์สำคัญถูกกลบ (Algorithm Burial):** อัลกอริทึมของโซเชียลมีเดียมักปิดกั้นหรือดันโพสต์ใหม่ๆ จนทำให้ประกาศสำคัญ หรือเรื่องเร่งด่วน (เช่น จอดรถขวางทาง) โดนกลบหายไปอย่างรวดเร็ว
* **❌ ร้องเรียนลอยๆ ไม่ได้รับการแก้ไข (Unresolved Complaints):** การโพสต์บ่นเรื่องงานซ่อมบำรุงหรือสิ่งชำรุดใน มอ. มักไปไม่ถึงเจ้าหน้าที่ที่เกี่ยวข้อง ปัญหาไม่ได้รับการแก้ไขจริงและกลายเป็นพื้นที่สะสมพลังลบ

### 2. แนวคิดผลิตภัณฑ์ (The Solution)
**UP Board** คือแพลตฟอร์มศูนย์รวมข่าวสารและประสานงานเฉพาะถิ่นแบบเบ็ดเสร็จสำหรับชาวมหาวิทยาลัยพะเยา ที่ออกแบบมาเพื่อแก้ปัญหาความวุ่นวายบนโซเชียลมีเดีย โดยเปลี่ยนฟีดที่ยุ่งเหยิงให้กลายเป็น **"กระดานดิจิทัลที่สดใหม่ เรียลไทม์ และจัดระเบียบชัดเจน"** เพื่อให้การกระจายข่าวสารและการจัดการปัญหาใน มอ. มีประสิทธิภาพสูงสุด

### 3. ฟีเจอร์เด่นที่เป็นจุดขาย (Key Value Propositions)
* **🗂️ แยกหมวดหมู่ฟีดเรียลไทม์ (Categorized Real-time Feed):** แยกหมวดหมู่โพสต์ชัดเจน *(กิจกรรม, ของหาย, บอกต่อของดี, เรื่องเร่งด่วน, แจ้งซ่อม)* เลือกดูได้ทันทีตามความสนใจ โดยไม่มีโฆษณาหรืออัลกอริทึมมาปิดกั้น
* **⏱️ ซ่อนจากหน้าแรกอัตโนมัติใน 24 ชั่วโมง (24-Hour Dashboard Auto-Hide):** โพสต์ทั่วไปจะซ่อนจากหน้าแรก (Dashboard) อัตโนมัติใน 24 ชั่วโมง (ยังค้นหาได้ในหน้าหมวดหมู่) เพื่อให้หน้าแรกสะอาด สดใหม่ทุกวัน และตัดปัญหาข้อมูลเก่าหรือดราม่าค้างปี — ระบบไม่ลบโพสต์ทิ้ง ส่วนกิจกรรมที่จะเริ่มภายใน 7 วันและงานแจ้งซ่อมที่ยังไม่เสร็จจะยังแสดงอยู่
* **📌 ระบบปักหมุดอัจฉริยะ (Smart Pinning System):** ระบบปักหมุดสำหรับประกาศที่เป็นทางการ ข่าวกิจกรรมคณะ หรือประกาศของหายสำคัญ เพื่อขยายเวลาให้อยู่บนหน้าแรกได้นานกว่าปกติ — ปักหมุดได้สูงสุด 72 ชั่วโมง (เจ้าหน้าที่ปักหมุดโพสต์ในคณะตัวเอง ผู้ดูแลระบบปักหมุดได้ทุกโพสต์)
* **🛠️ ระบบส่งต่อและติดตามงานซ่อม (Smart Maintenance Routing & Tracking):** เมื่อมีการแจ้งซ่อมพร้อมแนบรูปและระบุตำแหน่งตึก/คณะ เจ้าหน้าที่จะเห็นงานใหม่ทันที มอบหมายช่าง และอัปเดตสถานะ (รอดำเนินการ → รับเรื่อง → กำลังซ่อม → เสร็จสิ้น) พร้อมแจ้งเตือนในแอปกลับไปยังผู้แจ้งแบบเรียลไทม์ งานแจ้งซ่อมเปิดให้ผู้ใช้ที่ล็อกอินทุกคนเห็น เพื่อช่วยกันหลีกเลี่ยงจุดอันตราย โดยข้อมูลส่วนตัว (ตัวตนผู้แจ้ง พิกัด GPS ชื่อช่าง และบันทึกภายใน) เห็นได้เฉพาะผู้แจ้ง เจ้าหน้าที่ ผู้ดูแลระบบ และช่างที่ได้รับมอบหมาย

### 4. กลุ่มเป้าหมาย (Target Audience)
* **กลุ่มผู้ใช้หลัก:** นิสิตและบุคลากรมหาวิทยาลัยพะเยา *(ที่ต้องการอัปเดตข่าวสาร ประชาสัมพันธ์กิจกรรม หาของหาย หรือแจ้งเหตุเร่งด่วน)*
* **กลุ่มผู้ใช้ร่วม:** เจ้าหน้าที่ฝ่ายอาคารสถานที่ / งานซ่อมบำรุงของมหาวิทยาลัย *(ที่ใช้รับเรื่องร้องเรียน มีหน้า Dashboard จัดการงาน และส่งประกาศสำคัญระดับมหาวิทยาลัย)*

### 5. ผลกระทบที่คาดว่าจะได้รับ (Expected Impact)
* **🏛️ ด้านชุมชน (Community):** เกิดสังคมในรั้วมหาวิทยาลัยที่ช่วยเหลือกันและเข้าถึงข้อมูลได้รวดเร็ว แม่นยำ และปลอดภัยขึ้นผ่านพื้นที่กลางที่เป็นระเบียบ
* **⚡ ด้านการบริหารจัดการ (Efficiency):** ลดขั้นตอนและเพิ่มความเร็วในการทำงานของเจ้าหน้าที่ฝ่ายซ่อมบำรุงด้วยระบบคัดแยกพิกัดข้อมูลอัจฉริยะ ปัญหาใน มอ. ถูกแก้ไขจริง ไม่ใช่แค่การบ่นลอยๆ
* **🔥 ด้านความน่าสนใจ (Engagement):** ฟีเจอร์ซ่อนจากหน้าแรกอัตโนมัติใน 24 ชั่วโมง (ยังค้นหาได้ในหน้าหมวดหมู่) จะกระตุ้นความรู้สึกกลัวตกข่าว *(FOMO)* ทำให้ผู้ใช้งานอยากเปิดแอปพลิเคชันเข้ามาเช็กความเคลื่อนไหวใน มอ. ทุกวัน

## 🚀 เริ่มต้นใช้งาน (Getting Started)

### โครงสร้าง Repository (Monorepo)

```text
se-sec1-team-05/
├── frontend/     # Next.js + React + TypeScript (Deploy บน Vercel)
├── backend/      # Python + FastAPI + SQLAlchemy + Alembic, API และ Background Worker (Deploy บน Render)
├── database/     # Alembic migrations, seeders และ schema.sql อ้างอิง
├── docs/         # เอกสาร Requirements, Architecture, ADR และ API Contract
├── services/     # (ปลดระวางแล้ว) stats-service จาก Lab เดิม
└── src/          # (ปลดระวางแล้ว) โค้ด JavaScript จาก Lab เดิม
```

> ⚠️ `services/stats-service` และ `src/` เป็น **Lab Code เดิมที่ปลดระวางแล้ว (Retired)** เก็บไว้เป็นประวัติเท่านั้น ไม่ถูก Build หรือ Deploy อีกต่อไป (ดู [ADR-002](./docs/architecture/adr/002-business-rules-rbac-and-frontend-libraries.md))

### วิธีที่ 1: รันด้วย Docker Compose (แนะนำ — สำหรับพัฒนาบนเครื่องเท่านั้น)

```bash
cp .env.example .env        # แล้วแก้ทุกค่า (ต้องมี JWT_SECRET ยาว ≥ 32 ตัวอักษร)
docker compose up --build
```

ระบบจะรัน `db` (PostgreSQL) → `migrate` (Alembic + seed ข้อมูลอ้างอิงและข้อมูลตัวอย่าง) → `api` (FastAPI) + `worker` (APScheduler) + `frontend` (Next.js)

> หากมีไฟล์ `.env` เดิมอยู่แล้ว ให้เพิ่มตัวแปร `JWT_SECRET`, `BOOTSTRAP_ADMIN_EMAIL`, `BOOTSTRAP_ADMIN_PASSWORD` และ `DEMO_PASSWORD` ตาม `.env.example`

* **Frontend:** http://localhost:3000
* **API Docs (Swagger UI):** http://localhost:8000/docs

### วิธีที่ 2: รันโดยไม่ใช้ Docker

ต้องมี PostgreSQL ที่รันอยู่บนเครื่อง

**Backend (API):**

```bash
cd backend
python -m venv .venv
source .venv/bin/activate                  # Windows: .venv\Scripts\activate
pip install -r requirements-dev.txt
cp .env.example .env                       # แก้ DATABASE_URL, JWT_SECRET, BOOTSTRAP_ADMIN_*
alembic upgrade head
python ../database/seeders/seed.py --demo
uvicorn app.main:app --reload
```

**Background Worker** (เปิดอีก Terminal ในโฟลเดอร์ `backend/` และ Activate venv เดียวกัน):

```bash
python -m app.worker
```

**Frontend:**

```bash
cd frontend
npm ci
npm run dev
```

## 📅 กำหนดการและรูปแบบการประชุม (Meeting Cadence)

เพื่อสร้างความสมดุลระหว่างการเรียนและการพัฒนาโครงงาน ทีมเราเลือกใช้แนวทาง **"เน้นการสื่อสารแบบไม่พร้อมกันเป็นหลัก" (Async-first)** เพื่อลดภาระการจัดสรรเวลา แต่ยังคงรักษาความต่อเนื่องของงานไว้ได้

* **การประชุมประจำสัปดาห์และวางแผนสปรินต์ (แบบพร้อมหน้า - Synchronous)**
  * *วันเวลา / ระยะเวลา:* ทุกเย็นวันอาทิตย์ ใช้เวลา 45 นาที ผ่าน Discord หรือ MS Teams
  * *วัตถุประสงค์:* ทบทวนงานที่เสร็จสิ้นในสัปดาห์ที่ผ่านมา กำหนดเป้าหมายของสัปดาห์ถัดไป และย่อยงานออกเป็นส่วนกิจกรรมที่ชัดเจน *(เช่น การเขียนโค้ดสคริปต์ลบโพสต์ใน 24 ชั่วโมง, การตั้งค่าตรรกะสำหรับการคัดแยกหมวดหมู่)*
* **การรายงานความคืบหน้าแบบอัปเดตเอง (แบบไม่พร้อมหน้า - Asynchronous)**
  * *วันเวลา:* วันจันทร์ วันพุธ และวันศุกร์ (ส่งรายงานอัปเดตก่อนเวลา 13:00 น.)
  * *ช่องทาง:* ช่องแชท `#stand-up` ที่จัดไว้โดยเฉพาะ
  * *รูปแบบ:* โพสต์สรุปสั้น ๆ เป็นหัวข้อ 3 ประเด็น:
    1. *เมื่อวาน (Yesterday):* ทำอะไรเสร็จไปบ้าง?
    2. *วันนี้ (Today):* กำลังจะลุยงานส่วนไหนต่อ?
    3. *อุปสรรค (Blockers):* มีปัญหาอะไรที่ทำให้งานติดขัดไหม *(เช่น บั๊กในส่วนสถานะการปักหมุดโพสต์)?*
* **การทบทวนและสะท้อนผลการทำงาน (แบบพร้อมหน้า - Synchronous)**
  * *วันเวลา / ระยะเวลา:* ทุก ๆ สองสัปดาห์ (ควบรวมกับการประชุมประจำสัปดาห์ โดยเพิ่มเวลาอีก 15 นาที)
  * *วัตถุประสงค์:* สะท้อนมุมมองเกี่ยวกับกระบวนการทำงานว่ามีส่วนไหนที่ทำได้ดี อะไรที่ทำให้งานล่าช้า และร่วมกันตกลงแนวทางปรับปรุงกระบวนการทำงานให้ดีขึ้นอย่างเป็นรูปธรรม 1 ข้อสำหรับรอบถัดไป

## 💬 กฎเกณฑ์การสื่อสาร (Communication Rules)

เพื่อหลีกเลี่ยงความยุ่งเหยิงแบบเดียวกับที่เรากำลังแก้ปัญหาด้วยผลิตภัณฑ์ของเรา การสื่อสารภายในทีมจะต้องมีโครงสร้างที่เป็นระเบียบและชัดเจน

* **ช่องทางหลัก:** Discord / MS Teams สำหรับการพูดคุยด้านวิศวกรรมซอฟต์แวร์และการออกแบบโครงงานทั้งหมด
* **กรอบเวลาในการตอบกลับที่คาดหวัง:**
  * *ระดับทั่วไป:* ภายใน 12 ชั่วโมง
  * *งานด่วน / อุปสรรคเร่งด่วน:* ภายใน 3 ชั่วโมง
  * *หมายเหตุ:* หากติดเตรียมตัวสอบหรือมีงานคณะจำนวนมาก ให้แจ้งทีมล่วงหน้าเพื่อกระจายภาระงานใหม่
* **กฎเหล็กการใช้ Thread:** ห้ามส่งข้อความสแปมในช่องแชทหลักสำหรับการแก้บั๊กเชิงเทคนิคหรือการถกเถียงเรื่องการออกแบบ ให้สร้าง Thread ภายใต้หัวข้อที่เกี่ยวข้องเสมอ *(เช่น #ui-feedback หรือ #backend-routing)* เพื่อให้ข้อมูลค้นหาง่ายและอยู่เป็นหมวดหมู่
* **ช่องทางสาธารณะ กับ แชทส่วนตัว (DMs):** การเลือกสถาปัตยกรรมระบบ การออกแบบ API และการปรับเปลี่ยน UI ทั้งหมดต้องทำในช่องทางส่วนกลาง (Public Channels) ส่วนการทักแชทส่วนตัว (DM) ให้สงวนไว้สำหรับเรื่องเวลาว่างส่วนบุคคลหรือการนัดหมายเท่านั้น

## 🌿 กระบวนการทำงานด้วย Git และการตรวจทานโค้ด (Git Workflow & Code Review Process)

พวกเราใช้กระบวนการ GitHub Flow แบบเรียบง่าย เพื่อให้มั่นใจว่าสายพัฒนาหลัก (Production Branch) มีความเสถียร สะอาด และพร้อมปรับใช้งานจริงอยู่เสมอ

### กลยุทธ์การแยกสาขา (Branching Strategy)
* `main`: สาขาสำหรับโค้ดที่พร้อมใช้งานบน Production และมีความเสถียร **ห้ามคอมมิต (Commit) ตรงเข้าสู่ `main` โดยเด็ดขาด**
* สาขาการพัฒนาฟีเจอร์และแก้บั๊กจะต้องแยก (Cut) ออกมาจาก `main` โดยใช้รูปแบบการตั้งชื่อที่กำหนดไว้ชัดเจน:
  * `feat/ชื่อฟีเจอร์` *(เช่น feat/auto-delete-feed, feat/pin-announcement)*
  * `bugfix/ชื่อปัญหา` *(เช่น bugfix/fix-spam-filter-clash)*

### แนวทางการเขียนข้อความคอมมิต (Commit Message Guidelines)
พวกเราปฏิบัติตามมาตรฐาน Semantic Commit เพื่อให้ประวัติการทำงานใน Git ชัดเจนและอ่านง่าย:
* `feat: ...` สำหรับการเพิ่มฟีเจอร์หรือความสามารถใหม่ *(เช่น feat: integrate automated routing for maintenance reports)*
* `fix: ...` สำหรับการแก้ไขบั๊กหรือจุดบกพร่องในโค้ด *(เช่น fix: correct 24h timer expiration offset)*
* `docs: ...` สำหรับการอัปเดตเอกสารของโครงงาน *(เช่น docs: update setup variables in README)*

### กฎการส่ง Pull Request (PR) และตรวจทานโค้ด (Code Review)
* **การตรวจสอบตัวเอง (Self-Review):** ก่อนจะระบุตัวผู้ตรวจทาน ผู้เขียนโค้ดต้องเปิดดูประวัติการเปลี่ยนแปลง (PR diff) เพื่อตรวจสอบ console logs, โค้ดเก่าที่ไม่ได้ใช้ (dead code) หรือช่องว่างการจัดฟอร์แมตที่ผิดพลาดอีกครั้ง
* **การตรวจทานจากเพื่อนร่วมทีม (Peer Review):** ต้องมีสมาชิกในทีมอย่างน้อยหนึ่งคนทำการตรวจสอบ ทดสอบบนเครื่องตัวเองหากจำเป็น และอนุมัติ (Approve) PR นั้นก่อนจึงจะสามารถรวม (Merge) เข้าสู่สาขา `main` ได้
* **นโยบายโค้ดต้องผ่านฉลุย (Green Build Policy):** ห้ามรวม PR เข้าสู่ระบบหากทำให้การทดสอบระบบล้มเหลว (Failing Builds) หรือทำให้ส่วนประกอบโครงสร้างการกำหนดเส้นทางเดิมใช้งานไม่ได้

## ⚡ ขั้นตอนและข้อตกลงในการตัดสินใจ (Decision Making Protocol)
