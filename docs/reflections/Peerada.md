"จากแนวคิด 'Software Entropy' และ 'Broken Window Theory' ลองมองย้อนกลับไปในโปรเจกต์ที่คุณเคยทำ มี 'หน้าต่างที่แตก' บานไหนที่คุณเคยปล่อยปละละเลย และมันส่งผลกระทบอย่างไรในระยะยาว?"
= หน้าต่างที่แตกที่เคยปล่อยไว้คือการไม่จัดการ Technical Debt ตั้งแต่ต้น เช่น การเขียนโค้ดแบบ Hard Code และการคัดลอกโค้ดซ้ำหลายจุดเพื่อให้ฟังก์ชันใช้งานได้เร็วที่สุด ในช่วงแรกโปรเจกต์ยังทำงานได้ปกติ แต่เมื่อมีการเพิ่มฟีเจอร์และแก้ไขความต้องการของผู้ใช้ การแก้ไขโค้ดแต่ละครั้งต้องตามแก้หลายจุด ทำให้เกิดบั๊กใหม่บ่อยขึ้นและใช้เวลาในการพัฒนามากขึ้น สุดท้ายทีมต้องเสียเวลาปรับโครงสร้างโค้ดครั้งใหญ่ก่อนส่งงาน ซึ่งแสดงให้เห็นว่าการละเลยปัญหาเล็กๆ ในช่วงแรกส่งผลกระทบต่อคุณภาพและความสามารถในการดูแลรักษาระบบในระยะยาว

"อธิบายหลักการ 'Take Responsibility' ในความเข้าใจของคุณ และยกตัวอย่างสถานการณ์ที่คุณจะนำหลักการ 'Provide Options, Don't Make Lame Excuses' ไปใช้ในการสื่อสารกับเพื่อนร่วมทีมในโปรเจกต์นี้"
= หลักการ Take Responsibility คือ การรับผิดชอบต่อหน้าที่และผลลัพธ์ของงานตนเอง รวมถึงยอมรับข้อผิดพลาดและหาทางแก้ไข แทนการโทษผู้อื่นหรือปัจจัยภายนอก

ส่วนหลักการ "Provide Options, Don't Make Lame Excuses" คือ เมื่อพบปัญหา ควรเสนอแนวทางแก้ไขมากกว่าการให้ข้ออ้าง ตัวอย่างเช่น ในโปรเจกต์ Smart Caretaker หากข้อมูลสำหรับฝึก AI ไม่เพียงพอ หนูจะเสนอให้ใช้ชุดข้อมูลสาธารณะ ทดลองสร้างต้นแบบก่อน หรือปรับขอบเขตโครงการให้เหมาะสมกับข้อมูลที่มี เพื่อให้ทีมสามารถเดินหน้าต่อได้
