##  บริบทและเหตุผล (Context & Rationale)

โครงงาน **UP Board** เป็นเว็บแอปพลิเคชันสำหรับนิสิต บุคลากร เจ้าหน้าที่ฝ่ายซ่อมบำรุง และผู้ดูแลระบบของมหาวิทยาลัยพะเยา

ระบบมีวัตถุประสงค์เพื่อแก้ปัญหาข้อมูลข่าวสารบนสื่อสังคมออนไลน์ที่ปะปนและกระจัดกระจาย โดยจัดให้มีฟีดข่าวสารแบบแยกหมวดหมู่ เช่น:

* ข่าวกิจกรรม
* ของหาย
* บอกต่อของดี
* เรื่องเร่งด่วน
* การแจ้งซ่อม

### ฟีเจอร์และความสามารถสำคัญที่ระบบต้องรองรับ:

* **การสร้างและแสดงโพสต์ตามหมวดหมู่:** ผู้ใช้สามารถสร้างโพสต์และเลือกหมวดหมู่ของข้อมูลได้อย่างชัดเจน
* **การแสดงข้อมูลและสถานะงานแบบเรียลไทม์:** ผู้ใช้สามารถรับข้อมูลโพสต์ใหม่ ประกาศสำคัญ และการเปลี่ยนแปลงสถานะงานได้โดยไม่ต้องรีเฟรชหน้าเว็บตลอดเวลา
* **การกำหนดอายุโพสต์:** โพสต์ทั่วไปจะหมดอายุจากฟีดหลัง 24 ชั่วโมง โดยเปลี่ยนสถานะเป็น `expired` แทนการลบข้อมูลออกจากฐานข้อมูลทันที *(แก้ไขโดย ADR-002: ไม่เปลี่ยนสถานะโพสต์ แต่ซ่อนจาก Dashboard ณ เวลา Query และยังแสดงในหน้าหมวดหมู่)*
* **การปักหมุดประกาศ:** ผู้ดูแลระบบสามารถปักหมุดประกาศสำคัญ และกำหนดระยะเวลาการแสดงผลที่นานกว่าโพสต์ทั่วไป *(แก้ไขโดย ADR-002: Staff ปักหมุดโพสต์ในคณะตัวเองได้ และปักหมุดได้สูงสุด 72 ชั่วโมง)*
* **ระบบแจ้งซ่อม:** รองรับการแนบรูปภาพ รายละเอียดปัญหา และตำแหน่งของอาคารหรือพื้นที่ที่พบปัญหา
* **การมอบหมายงาน:** ผู้ดูแลระบบสามารถส่งต่องานซ่อมไปยังเจ้าหน้าที่ที่เกี่ยวข้อง
* **การติดตามสถานะ:** ผู้แจ้งและเจ้าหน้าที่สามารถติดตามและอัปเดตสถานะงานซ่อมได้
* **ระบบสิทธิ์ผู้ใช้ (RBAC):** กำหนดสิทธิ์ตามบทบาทของผู้ใช้งาน เช่น สมาชิกทั่วไป เจ้าหน้าที่ฝ่ายซ่อม ผู้ดูแลเนื้อหา และผู้ดูแลระบบ *(แก้ไขโดย ADR-002: เหลือ 3 บทบาท `student` / `staff` / `admin` — ผู้ดูแลเนื้อหารวมเข้ากับ admin และช่างซ่อมเป็นโปรไฟล์ `technicians` ของผู้ใช้ staff)*
* **ระบบแจ้งเตือน:** แจ้งเตือนเมื่อมีประกาศสำคัญ งานซ่อมใหม่ หรือสถานะงานเปลี่ยนแปลง

### ทักษะของทีมพัฒนาและข้อจำกัด:

* **ทักษะเดิมของทีม:** นิสิต 4 คน มีพื้นฐานด้าน JavaScript, React, TypeScript, Python, FastAPI และการพัฒนา REST API
* **ข้อจำกัดหลัก:**
  1. ระยะเวลาการพัฒนาภายใน 1 ภาคการศึกษา
  2. ทรัพยากรและงบประมาณของทีมมีจำกัด
  3. ความจำเป็นในการสร้างต้นแบบ (Prototype) และปรับปรุงระบบได้อย่างรวดเร็ว
  4. ทีมยังไม่มีสิทธิ์เข้าถึงระบบ University SSO หรือระบบยืนยันตัวตนอย่างเป็นทางการของมหาวิทยาลัย

##  การตัดสินใจ (Decision)

ทีมได้ตัดสินใจเลือกใช้เทคโนโลยีหลักดังต่อไปนี้:

| ส่วนของระบบ (Component) | เทคโนโลยีที่เลือก (Selected Tech) | รายละเอียดการใช้งาน |
| :--- | :--- | :--- |
| **Frontend** | **Next.js** + **React** + **TypeScript** | พัฒนาส่วนติดต่อผู้ใช้ ฟีดข่าว แบบฟอร์ม และ Dashboard |
| **Backend** | **Python** + **FastAPI** | พัฒนา REST API, Business Logic, Authentication และ File Upload |
| **Database** | **PostgreSQL** | Relational Database สำหรับเก็บข้อมูลที่มีความสัมพันธ์ |
| **ORM** | **SQLAlchemy** | ใช้เชื่อมต่อและจัดการข้อมูลระหว่าง FastAPI กับ PostgreSQL |
| **Database Migration** | **Alembic** | จัดการและติดตามการเปลี่ยนแปลงโครงสร้างฐานข้อมูล |
| **Real-time Communication** | **Server-Sent Events (SSE)** | ส่งโพสต์ใหม่ การแจ้งเตือน และสถานะงานจาก Backend ไปยัง Frontend |
| **File Storage** | **Local File Storage** → **S3-compatible Object Storage** | ใช้ Local Storage ในช่วงพัฒนา และเปลี่ยนเป็น Object Storage เมื่อนำไปใช้งานจริง |
| **Background Processing** | **APScheduler / Python Background Worker** | ตรวจสอบโพสต์หมดอายุและดำเนินงานตามเวลา |
| **Authentication** | **JWT Authentication + University Email Verification** | สมัครด้วยอีเมล `@up.ac.th` และเปิดใช้งานบัญชีหลังยืนยันอีเมล |
| **Password Hashing** | **Argon2** | Hash รหัสผ่านก่อนบันทึกลงฐานข้อมูล |
| **Authorization** | **Role-Based Access Control (RBAC)** | ตรวจสอบสิทธิ์ของผู้ใช้แต่ละบทบาทจาก Backend |
| **Deployment** | **Vercel** (Frontend) / **Render** (Backend) | แยก Deployment ของ Frontend และ Backend ออกจากกัน |

##  เหตุผลในการเลือกเทคโนโลยี (Rationale)

### 1. Frontend: Next.js + React + TypeScript

* **Interaction สูง:** UP Board ต้องการส่วนติดต่อผู้ใช้ที่มีการโต้ตอบสูง เช่น ฟีดข่าวแบบแยกหมวดหมู่ แบบฟอร์มสร้างโพสต์ ระบบแจ้งซ่อม หน้า Dashboard ของเจ้าหน้าที่ และหน้าจัดการระบบของผู้ดูแล
* **Reusable Components:** React สนับสนุนการสร้าง Component ที่สามารถนำกลับมาใช้ซ้ำได้ เช่น `PostCard`, `CategoryFilter`, `MaintenanceStatus` และ `NotificationComponent`
* **Type Safety:** TypeScript ช่วยตรวจสอบชนิดข้อมูลก่อนรันโปรแกรม ลดข้อผิดพลาดระหว่างการรับส่งข้อมูลกับ Backend API และช่วยให้สมาชิกในทีมทำงานร่วมกันได้ง่ายขึ้น
* **Project Structure:** Next.js ช่วยจัดโครงสร้างโปรเจกต์ การกำหนดเส้นทางของหน้า (Routing) การจัดการ Layout และการแยกส่วนของหน้าเว็บอย่างเป็นระบบ

### 2. Backend: Python + FastAPI

* **พัฒนาได้รวดเร็ว:** FastAPI เหมาะกับการพัฒนา REST API อย่างรวดเร็ว รองรับการตรวจสอบข้อมูล การอัปโหลดไฟล์ Authentication และการสื่อสารแบบ Server-Sent Events
* **Data Validation:** FastAPI ใช้ Pydantic สำหรับตรวจสอบข้อมูล Request และ Response ช่วยลดโอกาสที่ข้อมูลไม่ถูกต้องจะเข้าสู่ระบบ
* **Auto Interactive Docs:** FastAPI สร้างเอกสาร API ผ่าน Swagger UI และ OpenAPI ให้อัตโนมัติ ทำให้ทีม Frontend สามารถตรวจสอบและทดลองเรียกใช้ API ได้สะดวก
* **ใช้งานง่าย:** Python มีรูปแบบคำสั่งที่อ่านง่าย สมาชิกในทีมสามารถใช้พัฒนา Business Logic และงานเบื้องหลัง เช่น การตรวจสอบโพสต์หมดอายุและการแจ้งเตือนได้
* **ตรงกับทักษะทีม:** สมาชิกมีพื้นฐาน Python และ FastAPI อยู่แล้ว จึงช่วยลด Learning Curve และเหมาะกับข้อจำกัดด้านเวลา

ทีมเลือก FastAPI เนื่องจากเหมาะกับทักษะและข้อจำกัดของทีม ไม่ได้หมายความว่า Node.js หรือ Express ไม่สามารถนำมาใช้พัฒนาระบบนี้ได้

### 3. Database: PostgreSQL

* **โครงสร้างชัดเจน:** ข้อมูลของ UP Board มีโครงสร้างและความสัมพันธ์กันอย่างชัดเจน จึงเหมาะกับฐานข้อมูลแบบ Relational Database
* **ความสัมพันธ์ของข้อมูล (Data Relationships):**
  * ผู้ใช้ 1 คน → สามารถสร้างได้หลายโพสต์
  * โพสต์ 1 รายการ → อยู่ใน 1 หมวดหมู่
  * ผู้ใช้ 1 คน → สามารถสร้างรายการแจ้งซ่อมได้หลายรายการ
  * งานแจ้งซ่อม 1 รายการ → สามารถมีประวัติสถานะได้หลายรายการ
  * เจ้าหน้าที่ 1 คน → สามารถรับผิดชอบงานซ่อมได้หลายงาน
  * ผู้ดูแลระบบ 1 คน → สามารถตรวจสอบ ปักหมุด หรือซ่อนโพสต์ได้หลายรายการ
* **Data Integrity:** PostgreSQL รองรับ Transaction, Foreign Key, Unique Constraint และ Check Constraint ซึ่งช่วยรักษาความถูกต้องและความสอดคล้องของข้อมูล
* **เหมาะกับ Workflow งานซ่อม:** การเปลี่ยนสถานะ การมอบหมายงาน และการบันทึกประวัติจำเป็นต้องมีความถูกต้องและสามารถตรวจสอบย้อนหลังได้
* **การจัดการผ่าน ORM:** SQLAlchemy ช่วยให้ Backend จัดการข้อมูลผ่าน Model ได้อย่างเป็นระบบ ส่วน Alembic ใช้ควบคุมการเปลี่ยนแปลงโครงสร้างฐานข้อมูลของสมาชิกทุกคนในทีม

### 4. Deployment Model

* **การแยก Deployment:** แยกการ Deploy ระหว่าง Frontend และ Backend
  * **Frontend:** Deploy บน **Vercel** เนื่องจากรองรับ Next.js โดยตรง ตั้งค่าได้ง่าย และเหมาะกับการสร้างต้นแบบและสาธิตผลงาน
  * **Backend:** Deploy บนแพลตฟอร์มที่รองรับ Python คือ Render
  * **Database:** ใช้ PostgreSQL ที่แยกออกจาก Frontend และ Backend
* **ประโยชน์:** ช่วยให้แต่ละส่วนสามารถพัฒนา ทดสอบ และปรับปรุงได้อย่างอิสระ
* **ข้อกำหนดเพิ่มเติม:** ทีมต้องกำหนด CORS, Environment Variables, API Base URL และ Database Connection ให้ถูกต้อง

##  ผลที่ตามมาจากการตัดสินใจ (Consequences)

###  ผลเชิงบวก (Positive Consequences)

1. **ตรงกับทักษะทีม:** สอดคล้องกับทักษะเดิมของสมาชิกในทีม ช่วยลดเวลาในการเรียนรู้
2. **สร้าง Prototype ได้รวดเร็ว:** Next.js และ FastAPI เหมาะกับการพัฒนาภายในระยะเวลาจำกัด
3. **UI/UX มีประสิทธิภาพ:** Next.js และ React เหมาะกับการสร้างหน้าเว็บที่มีการโต้ตอบและ Dashboard
4. **ลด Code ซ้ำซ้อน:** React Component สามารถนำกลับมาใช้ซ้ำได้
5. **ลด Bugs:** TypeScript และ Pydantic ช่วยลดข้อผิดพลาดเกี่ยวกับชนิดข้อมูล
6. **พัฒนา API ได้เร็ว:** FastAPI ช่วยให้พัฒนาและทดสอบ REST API ได้รวดเร็ว
7. **Integration ง่าย:** Swagger UI ช่วยให้ Frontend ตรวจสอบและทดลองใช้ API ได้สะดวก
8. **จัดการข้อมูลซับซ้อนได้ดี:** PostgreSQL เหมาะสมกับความสัมพันธ์ระหว่างผู้ใช้ โพสต์ หมวดหมู่ และงานแจ้งซ่อม
9. **จัดการฐานข้อมูลอย่างเป็นระบบ:** SQLAlchemy และ Alembic ช่วยควบคุม Model และ Database Migration
10. **พัฒนาแยกกันได้:** Frontend และ Backend สามารถพัฒนาและ Deploy แยกกันได้
11. **รองรับการอัปเดตข้อมูล:** SSE รองรับการส่งโพสต์ใหม่และสถานะงานจาก Backend ไปยัง Frontend
12. **รองรับการขยายตัว:** ระบบสามารถเปลี่ยนไปใช้ Object Storage, Message Queue หรือ University SSO ได้ในอนาคต หากมีความจำเป็นและได้รับสิทธิ์
13. **ไม่บล็อก API หลัก:** การใช้ Background Worker ช่วยให้งานตามเวลาไม่รบกวนการตอบสนองของ API หลัก

###  ผลเชิงลบและข้อแลกเปลี่ยน (Negative Consequences & Trade-offs)

1. **การแยก Environment:** การแยก Frontend และ Backend ทำให้ต้องตั้งค่า Deployment และ Environment แยกกัน
2. **การตั้งค่า CORS:** ต้องกำหนดค่า CORS ให้ถูกต้องเพื่อให้ Frontend เรียกใช้งาน Backend ได้ โดยไม่เปิดสิทธิ์กว้างเกินความจำเป็น
3. **ความปลอดภัยของ Token:** ระบบ Authentication ด้วย JWT ต้องมีการจัดการ Token วันหมดอายุ และ Secret อย่างปลอดภัย
4. **ความซับซ้อนของ Connection:** การใช้ SSE เพิ่มภาระด้านการจัดการ Connection ที่เปิดค้างและการเชื่อมต่อใหม่เมื่อ Connection หลุด
5. **ความต่อเนื่องของ Background Task:** Background Worker ต้องทำงานอย่างต่อเนื่องเพื่อให้ระบบหมดอายุโพสต์และแจ้งเตือนทำงานถูกต้อง
6. **ข้อจำกัดของ Local Storage:** Local File Storage เหมาะเฉพาะช่วงพัฒนา และไฟล์อาจสูญหายเมื่อ Server Redeploy หรือ Restart
7. **ข้อจำกัดของ Free Tier:** แพ็กเกจฟรีของแพลตฟอร์ม Deployment อาจมีข้อจำกัดด้านทรัพยากร Sleep Mode หรือ Cold Start
8. **ข้อจำกัดของ Email Verification:** การยืนยันอีเมล `@up.ac.th` สามารถพิสูจน์ได้ว่าผู้ใช้เข้าถึงอีเมลนั้น แต่ไม่สามารถตรวจสอบได้โดยตรงว่ายังเป็นนิสิตหรือบุคลากรอยู่ในปัจจุบันเหมือน University SSO
9. **ภาระการดูแลระบบ:** ทีมต้องดูแลและ Deploy Frontend, Backend, Database, Background Worker และ File Storage แยกจากกัน
10. **ต้องกำหนดนโยบายข้อมูล:** ทีมต้องกำหนดนโยบายการเก็บรักษาโพสต์หมดอายุ รูปภาพ ประวัติงานซ่อม และ Audit Log ให้ชัดเจน

##  ประเด็นด้านความปลอดภัย (Security Considerations)

* **ห้ามจัดเก็บ Secrets บน Git:** ห้ามจัดเก็บ Password, API Key, JWT Secret, Email Credential หรือ Database Credential ไว้ใน Git Repository
* **การใช้ Environment Variables:** ข้อมูลลับต้องเก็บไว้ใน Environment Variables หรือระบบ Secrets Management และไฟล์ `.env` ต้องอยู่ใน `.gitignore`
* **Password Hashing:** Password ของผู้ใช้งานต้องผ่านการ Hash ด้วย Argon2 ก่อนบันทึกลงฐานข้อมูล ห้ามเก็บรหัสผ่านแบบ Plain Text
* **University Email Verification:** ระบบต้องตรวจสอบ Domain `@up.ac.th` แบบตรงตัว และเปิดใช้งานบัญชีหลังจากผู้ใช้ยืนยันอีเมลแล้วเท่านั้น
* **การยืนยันอีเมล:** (แก้ไขตาม ADR-003) ไม่ใช้ลิงก์ยืนยันทางอีเมลแล้ว — ยืนยันด้วยการเข้าสู่ระบบด้วย Google (@up.ac.th) ครั้งแรก
* **Role Assignment:** ผู้สมัครใหม่จะได้รับ Role เริ่มต้นเป็นสมาชิกทั่วไป และไม่สามารถกำหนดตนเองเป็นเจ้าหน้าที่หรือ Admin ได้
* **Backend RBAC Validation:** Backend ต้องตรวจสอบสิทธิ์ตามบทบาทของผู้ใช้ทุกครั้ง การซ่อนปุ่มใน Frontend เพียงอย่างเดียวไม่ถือว่าเป็นการป้องกันสิทธิ์
* **JWT Security:** JWT ต้องมีวันหมดอายุ มีลายเซ็นที่ตรวจสอบได้ และใช้ Secret ที่มีความปลอดภัย
* **HTTPS:** ระบบที่นำไปใช้งานจริงต้องสื่อสารผ่าน HTTPS
* **File Upload Security:** Backend ต้องตรวจสอบขนาดไฟล์ ประเภทไฟล์ MIME Type และเปลี่ยนชื่อไฟล์ก่อนจัดเก็บ
* **Data Access Restriction:** รูปภาพแจ้งซ่อม ข้อมูลตำแหน่ง และประวัติงานต้องเปิดให้เข้าถึงเฉพาะผู้ที่มีสิทธิ์ *(แก้ไขโดย ADR-002: งานแจ้งซ่อมเปิดให้ผู้ใช้ที่ล็อกอินทุกคนเห็นข้อมูลสาธารณะ — หัวข้อ รายละเอียด ตำแหน่งแบบข้อความ สถานะ และรูปที่ลบ EXIF/GPS แล้ว ส่วนตัวตนผู้แจ้ง พิกัด GPS ชื่อช่าง และบันทึกสถานะภายใน ยังจำกัดเฉพาะผู้มีสิทธิ์ โดย Backend กรองฟิลด์ใน Response Schema)*
* **Sanitize Architecture Diagram:** Architecture Diagram ต้องไม่ระบุ IP Address, Password, Server Name, Internal Port หรือ Database Endpoint จริง
* **Audit Trail:** การปักหมุด ลบ ซ่อนโพสต์ เปลี่ยน Role มอบหมายงาน และเปลี่ยนสถานะงานควรมีประวัติสำหรับตรวจสอบย้อนหลัง

##  เงื่อนไขในการทบทวนการตัดสินใจ (Review Triggers)

ควรทบทวน ADR ฉบับนี้เมื่อเกิดเหตุการณ์ต่อไปนี้:

1. จำนวนผู้ใช้งานหรือการเชื่อมต่อแบบเรียลไทม์เพิ่มขึ้นอย่างมาก
2. มหาวิทยาลัยเปิดให้เชื่อมต่อระบบยืนยันตัวตนอย่างเป็นทางการ
3. เปลี่ยนจาก Local File Storage ไปเป็น Cloud Object Storage
4. งานเบื้องหลังมีความซับซ้อนจน APScheduler ไม่เพียงพอ
5. ระบบต้องรองรับผู้ใช้งานจริงในระดับมหาวิทยาลัย
6. ระบบต้องเปลี่ยนไปใช้ Redis, Celery หรือ Message Queue
7. ระบบเพิ่มฟีเจอร์ที่ต้องสื่อสารสองทางอย่างต่อเนื่อง เช่น ระบบ Chat
8. มีการเปลี่ยนแพลตฟอร์ม Deployment หรือโครงสร้างระบบครั้งสำคัญ
9. มีข้อกำหนดด้านความปลอดภัยหรือการคุ้มครองข้อมูลเพิ่มเติม
10. ค่าใช้จ่ายหรือข้อจำกัดของแพลตฟอร์ม Cloud เปลี่ยนแปลงอย่างมีนัยสำคัญ
