# ADR-003: บทบาท 6 แบบ, ขั้นตอนงานซ่อม, กฎ Spam, สาขาวิชา/ช่องทางติดต่อ และการจัดการรายงาน

- **สถานะ:** ✅ ยอมรับแล้ว (Accepted) — Amends ADR-002 (แทนที่ RBAC 3 บทบาท กฎ Spam ตามช่วงเวลา และ state machine งานซ่อมเดิม)
- **ที่มา:** โค้ดใน `backend/app` อ้างอิงเอกสารนี้ (`core/permissions.py`, `services/spam.py`, `services/repairs.py`, `services/moderation.py`)

## บริบทและเหตุผล

ADR-002 กำหนดบทบาท student / staff / admin ซึ่งไม่พอสำหรับการใช้งานจริง (อาจารย์, สโมสรนิสิต, กองอาคาร, ช่างซ่อม) และงานซ่อมที่ผ่านการตรวจรับก่อนปิดงาน จึงปรับกฎดังนี้

## การตัดสินใจ

### 1. บทบาท 6 แบบ (คงที่ ห้ามเพิ่ม/ลด)

`student`, `teacher`, `technician`, `building_staff`, `student_club`, `admin`

- **ต้องสมัครสมาชิกก่อนเข้าสู่ระบบครั้งแรก** (ผู้ใช้ตัดสินใจ ตั้งใจต่างจาก spec §2.1 ที่ให้ Google สร้างบัญชีอัตโนมัติ): ผู้ใช้สมัครด้วยอีเมล @up.ac.th + รหัสผ่านของตัวเอง + **คณะ + สาขาวิชา** ได้บทบาทตามอีเมล (รหัสนิสิตขึ้นต้นด้วยตัวเลข = `student`, อีเมลบุคลากร = `teacher`) และโปรไฟล์ครบทันที **การยืนยันอีเมลทำด้วย Google ไม่มีการส่งอีเมล** (ผู้ใช้ตัดสินใจ): บัญชีที่สมัครใหม่ `is_verified=false` เข้าสู่ระบบด้วยรหัสผ่านไม่ได้ (403 `EMAIL_NOT_VERIFIED`) จนกว่าจะเข้าสู่ระบบด้วย Google (@up.ac.th) ครั้งแรก ซึ่งพิสูจน์ว่าเป็นเจ้าของกล่องอีเมล และเพื่อกันคนแอบสมัครด้วยอีเมลของผู้อื่น บัญชีที่สมัครด้วยรหัสผ่านและยังไม่ยืนยันต้องส่งรหัสผ่านที่ตั้งไว้ตอนสมัครมาด้วยหนึ่งครั้ง (403 `PASSWORD_CONFIRMATION_REQUIRED`) บัญชีที่ admin สร้างให้ (ไม่มีรหัสผ่าน) ไม่ต้อง; admin ยืนยันให้เองได้ ตารางและ endpoint ลิงก์ยืนยันอีเมลถูกลบ หลังยืนยันแล้วเข้าสู่ระบบด้วยรหัสผ่านหรือ Google ก็ได้ Google ไม่สร้างบัญชีใหม่ (อีเมลที่ยังไม่สมัคร → 403 `NOT_REGISTERED`); endpoint onboarding คงไว้สำหรับบัญชีเก่าที่ยังไม่ครบ (403 `PROFILE_INCOMPLETE`)
- `technician`, `building_staff`, `student_club`, `admin` ถูก **Admin สร้างบัญชีล่วงหน้า** (`POST /admin/users`, ไม่มีรหัสผ่าน) แล้วเจ้าของล็อกอินด้วย Google; `student_club` ใช้อีเมลที่ไม่ใช่ @up.ac.th ได้
- บัญชี admin / demo ที่ seeder สร้างเท่านั้นที่ใช้อีเมล + รหัสผ่าน

### 3. ขั้นตอนงานซ่อม (repair flow)

```
open ──มอบหมายช่าง──▶ assigned ──▶ in_progress ──▶ pending_review ──▶ closed
                                       ▲                │
                                       └── ส่งกลับ ─────┘     (สถานะที่ยังไม่จบ) ──▶ rejected
```

- งานซ่อมเป็นสาธารณะสำหรับผู้ล็อกอิน แต่ผู้แจ้ง, GPS, ช่าง และ note ภายในเห็นเฉพาะผู้มีสิทธิ์ ต้องแนบรูปอย่างน้อย 1 รูปตอนแจ้ง
- `open → assigned` เกิดจากการมอบหมายช่างเท่านั้น; มอบหมายซ้ำได้ขณะ open / assigned / in_progress (งานที่กำลังทำจะกลับเป็น `assigned`)
- ช่าง: assigned → in_progress → pending_review พร้อม note และรูป `repair_after` เท่านั้น
- กองอาคาร: ปิดงานที่ `pending_review` หรือส่งกลับ `in_progress` (ต้องมี note) และปฏิเสธจากสถานะที่ยังไม่จบ (ต้องมีเหตุผล ≥ 3 ตัวอักษร); `closed` / `rejected` เป็นสถานะสุดท้าย
- ผิดลำดับ → 409 `INVALID_TRANSITION`; ทุกการเปลี่ยนล็อกแถวด้วย `SELECT … FOR UPDATE` และบันทึกใน `repair_status_history`
- แจ้งซ่อมถี่เกินไป (ค่าเริ่มต้นห่างกันอย่างน้อย 120 วินาที) → 429 `REPAIR_TOO_FAST`; ประกาศ (announcement) ผูกกับงานซ่อมได้ด้วย `related_repair_id`

### 4. กฎ Spam (แทนที่กฎช่วงเวลาเดิม)

- นับเฉพาะโพสต์ `general` ที่ **ติดกัน** ในวันปฏิทิน Asia/Bangkok เดียวกัน (รวมโพสต์ที่เพิ่งสร้าง; โพสต์ที่ถูกลบแบบ soft ยังนับ)
- โพสต์ประเภทอื่นคั่น (event, announcement, repair, lost_found) = เริ่มนับใหม่
- **ครบ 3 → แจ้งเตือน** (โพสต์ยังถูกสร้าง) และ **ครบ 5 → ระงับการโพสต์ 1 วันปฏิทิน** กลับมาโพสต์ได้ 00:00 น. (เวลาไทย) ของวันถัดไป — ไม่มีระดับที่สูงกว่านี้ (ไม่มีการระงับ 7 วัน)
- โพสต์ก่อนเวลาสิ้นสุดของการระงับล่าสุด (หรือเวลาที่ admin ปลดให้ก่อน) ไม่นับ จึงเริ่มชุดใหม่ และเตือนที่ 3 ได้อีก
- ระหว่างระงับ โพสต์ได้ทุกประเภทไม่ได้ (403 `POSTING_SUSPENDED`, `details[0].message` = เวลาที่กลับมาโพสต์ได้) แต่ยังอ่านและดูประวัติได้
- ประวัติเก็บใน `posting_violations` / `posting_suspensions` (ไม่ลบ); Admin ปลดได้ด้วย `PATCH /admin/users/{id}` `{lift_suspension:true}`
- ล็อกแถวผู้ใช้ (`FOR UPDATE`) ระหว่างสร้างโพสต์ เพื่อให้ request พร้อมกันถูกประเมินทีละอัน; ปิดกฎได้ด้วย `SPAM_POLICY_ENABLED=false` (เฉพาะการทดสอบ)

### 5. กฎการปักหมุด

- ปักได้เฉพาะ `event` (โดย `student_club` เจ้าของ) และ `announcement` (โดย `building_staff` เจ้าของ); admin ปักได้ทุกโพสต์ประเภทนี้
- ผู้ปักเลือก 6 / 12 / 24 / 48 / 72 ชั่วโมง (ค่าเริ่มต้น 48) ปักซ้ำได้ ไม่มีกรอบ 72 ชม. รวม
- อีเวนต์ปักได้ก่อนเริ่มเท่านั้น และหมุดไม่เกินเวลาเริ่มอีเวนต์; ประกาศที่ผูกงานซ่อมปักค้างจนงานซ่อมปิด/ถูกปฏิเสธ
- ไม่ผ่านเงื่อนไข → 409 `PIN_NOT_ELIGIBLE`

### 6. คณะ / สาขาวิชา และช่องทางติดต่อ

- ตาราง `faculties` และ `programs` (สาขาวิชา, `faculty_id`, `code` คงที่, `is_active`) — **ไม่ลบ แต่ปิดการใช้ด้วย `is_active=false`**; Admin จัดการที่ `/admin/faculties`, `/admin/programs`
- ผู้ใช้เลือกคณะ + สาขาวิชา (สาขาต้องอยู่ในคณะนั้นและยัง active) ไม่มีชั้นปีอีกต่อไป
- Seeder ใส่รายการคณะ/สาขาตามรายการทางการของ มพ. ที่ทีมจัดหา แบบรันซ้ำได้ (เพิ่มเฉพาะที่ยังไม่มี ไม่เขียนทับ) และปิดการใช้สาขาตัวอย่างเก่าที่ไม่อยู่ในรายการ
- ช่องทางติดต่อ (Facebook / Instagram / LINE) ผู้ใช้แก้เองที่ `PATCH /auth/me` และผู้ล็อกอินคนอื่นดูได้ที่ `GET /users/{id}` เฉพาะช่องที่กรอก

### 7. การจัดการรายงาน (reports)

- ผู้ใช้รายงานโพสต์คนอื่นได้ 1 ครั้งต่อโพสต์ (ซ้ำ → 409 `DUPLICATE_REPORT`) และดูรายงานของตัวเองได้ที่ `/reports/mine`
- Admin ทำได้ 2 การกระทำ: **ลบเนื้อหา** (`content_removed` — soft delete โพสต์และปิดรายงานอื่นที่เปิดอยู่ของโพสต์นั้น) หรือ **ปิดรายงานโดยไม่ลบ** (`dismissed`) ทั้งสองทำได้จาก `reported` / `under_review` / `upheld` (สองสถานะหลังเหลือไว้สำหรับรายงานเดิม)
- ทุกขั้นตอนบันทึกใน `report_actions` และแจ้งผู้รายงาน; โพสต์ที่ถูกลบยังเก็บประวัติรายงาน

## ผลที่ตามมา

- (+) สิทธิ์ชัดเจนต่อบทบาท, งานซ่อมมีขั้นตรวจรับ, กฎ Spam เข้าใจง่ายและตรวจสอบย้อนหลังได้
- (−) ต้องดูแลรายการคณะ/สาขาผ่านหน้า admin เมื่อมหาวิทยาลัยเปลี่ยนหลักสูตร; บัญชีพิเศษต้องให้ admin สร้างเอง

## เงื่อนไขในการทบทวน

- ต้องมีบทบาทใหม่ หรือเกณฑ์ Spam ปรับ (จำนวนโพสต์ / ระยะเวลาระงับ)
- รายการสาขาวิชาทางการเปลี่ยน
